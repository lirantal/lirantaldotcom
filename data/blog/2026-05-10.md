The pitch is seductive: describe what you want, let the agent write the code, ship faster. And the productivity gains are real. But six months into daily coding-agent workflows across production codebases, a pattern has crystallized that the "AI replaces developers" narrative conveniently ignores. The developers who extract the most value from LLM-powered tools are the ones who already know what good code looks like, how systems should be structured, and which conventions their codebase follows. Technical proficiency is not the thing these tools replace. It is the thing that makes them useful.

Without that grounding, you are not steering—you are accepting. And what you accept from a coding agent that lacks your project context, your architectural history, and your failure scars is often subtly wrong in ways that compound over time.

## Background: The LLM-as-Augmentation Thesis

The framing matters. LLMs are augmentation tools, not replacement engines. When you provide more data and context to a model, its outputs improve. That is not a revelation—it is a direct consequence of how attention mechanisms and in-context learning work. But "providing context" is not a passive act. It requires knowing what context is relevant, which architectural decisions the model might violate, and where the boundaries of a particular abstraction sit.

This maps to what we have seen in practice across every major model and agent framework: [Cursor](https://www.cursor.com/), Claude Code, GitHub Copilot, Windsurf, and others. The agent writes code faster than you can type it. But the agent does not know that your team migrated off a particular pattern three months ago, or that a given module uses dependency injection for testability reasons, or that a helper function already exists two directories over. That is your job. That has always been your job. The tool changed; the job did not.

The prior art here stretches back to any productivity tool in software. IDEs with autocomplete did not make understanding APIs optional. Static analysis tools did not make understanding type systems optional. CI pipelines did not make understanding deployment topology optional. Each tool raised the floor for what a developer could accomplish per unit of time. None lowered the ceiling on what you needed to know.

## How Steering Actually Works

Experienced developers interact with coding agents differently than newcomers. The difference is not in prompt engineering technique—it is in knowing what to ask for and recognizing when the output is wrong.

Consider a concrete scenario. You ask an agent to re-order output sections in a reporting module so that contributors appear right after the activity section. The agent explores the codebase, finds the render function, moves the relevant `lines.push(...)` blocks, runs the test suite, confirms it passes, and presents the diff.

![A coding agent re-ordering output sections in a codebase — the developer steers the structural change with a specific instruction because they know the report's intended reading order](/images/blog/coding-agents-output-section-reordering.png)

That interaction only works because the developer knew the intended reading order of the report. The agent did not invent that order. It executed a structural refactoring guided by someone who understood what "right after the activity section" meant in context. Without that specificity, the agent either guesses (often wrong) or asks clarifying questions that you cannot answer without the same domain knowledge you would need to write the code yourself.

The same pattern repeats when you push the agent toward correct integration patterns. In another session, investigating how to run database migrations programmatically for integration tests, the agent browses upstream documentation, finds the right API (`migrate` from `drizzle-orm/pglite/migrator`), and proposes a clean implementation that reads migration files from a directory and applies them—no hardcoded SQL, no shelling out to a CLI.

![A coding agent discovering the correct Drizzle ORM migration API after the developer challenges its initial approach — experience tells you when to push back](/images/blog/coding-agents-drizzle-orm-migration.png)

But that outcome only arrived because the developer challenged the agent's initial approach. The first suggestion involved hardcoded SQL in the test setup file. An experienced engineer recognized that as a maintenance smell and redirected: "Did you plan to actually read the migration files and execute them? You cannot simply use the `db:migrate` npm script or the drizzle-kit CLI in this way." The agent corrected course. The correction came from the human, not the machine.

This is what steering looks like in practice. It is not typing prompts into a box and hoping. It is an iterative dialogue where the developer's experience acts as a constraint function—rejecting outputs that violate conventions, redirecting toward patterns that match the project's architecture, and validating that the final result is something you would have written yourself (just faster).

## The Experience Gap in Agent Interactions

When a developer lacks the technical proficiency to evaluate an agent's output, a few failure modes emerge consistently:

- **Convention drift.** The agent writes code that works but does not follow the project's established patterns. Over time, the codebase accumulates inconsistencies that make future changes harder. No linter catches "we use repository pattern here, not active record."
- **Hidden dependency on outdated patterns.** The agent's training data includes deprecated approaches, old API versions, and patterns that the community has moved past. Without knowing the current state of the art, you cannot recognize when the agent is two years behind.
- **Missing tests for the right thing.** The agent can generate test code, but an inexperienced developer may not realize that the generated tests exercise the happy path while ignoring the edge cases that matter. If AI can write code, it can write test code too—but the question of *what* to test still requires engineering judgment.
- **Subtle architectural violations.** The agent does not know that a particular module intentionally avoids a framework feature for performance reasons. It will cheerfully re-introduce the abstraction you spent a sprint removing.

Each of these failure modes produces code that passes CI, looks reasonable in a PR, and slowly degrades the system. The cost is not immediate. It is cumulative.

## Trade-offs: Speed Versus Correctness

The core trade-off in agent-assisted development is between velocity and engineering integrity. Every team calibrates this differently based on project maturity, risk tolerance, and the experience level of the humans in the loop.

| Approach | Speed | Correctness risk | When it fits |
| --- | --- | --- | --- |
| Accept agent output with minimal review | Very high | High — convention drift, subtle bugs | Throwaway prototypes, exploratory spikes |
| Agent writes, developer reviews each diff | High | Moderate — catches obvious issues, misses deep ones | Feature branches with experienced reviewers |
| Developer outlines architecture, agent implements within constraints | Moderate-high | Low — the human defines the structure | Production systems with clear conventions |
| Developer writes critical paths, agent handles boilerplate | Moderate | Very low — creative work stays human-directed | Systems with safety or correctness requirements |

The right quadrant is not always the bottom row. Speed matters. Prototypes should ship fast. But for production systems that carry users, revenue, or security guarantees, the developer's job is not to go faster. It is to go correctly—and use the agent to reduce the toil of getting there.

## Applications: Where Proficiency Multiplies Agent Output

The amplification effect is clearest in specific categories of work:

**Refactoring with intent.** You know the target architecture. The agent has the patience to find every call site, update every import, run the tests, and chase down type errors across thirty files. Your proficiency defines the target state. The agent executes the migration. Without proficiency, you are refactoring toward... what, exactly?

**Code review acceleration.** You use the agent to generate a first-pass review—style issues, potential null dereference, missing error handling. But you still need to evaluate whether the agent's suggestions are relevant to *your* system's contracts. A suggestion to "add null check here" might be wrong if the type system guarantees non-null at that boundary.

**Learning new territory.** The agent excels at synthesizing documentation, showing API usage examples, and explaining unfamiliar libraries. But you need enough baseline knowledge to ask the right questions and evaluate whether the answers are current. If you have never worked with database migrations programmatically, you might accept a hardcoded SQL approach without knowing that a proper migration runner exists.

**Security auditing augmentation.** Agents can scan for common vulnerability patterns—hardcoded secrets, SQL injection vectors, path traversal. But understanding whether a flagged pattern is actually exploitable in your specific deployment context requires the kind of threat modeling that only comes from experience with [production incidents and security research](https://www.nodejs-security.com/).

## Validation: How to Know the Agent Got It Right

Accepting agent output without verification is the failure mode this entire argument warns against. Here are concrete validation practices:

- **Run the test suite after every agent-generated change.** This is obvious but often skipped during rapid iteration. If your tests pass, you have a baseline. If you have no tests, the agent just wrote untested code into your production path.
- **Diff against your mental model.** Before accepting a generated diff, ask: "Is this how I would have structured it?" If yes, the agent saved you time. If no, investigate why. The agent may have found a better approach, or it may have violated a constraint it does not know about.
- **Check for convention adherence.** Does the generated code use the patterns established in neighboring modules? Does it import from the right locations? Does it follow the naming conventions? Agents do not read your team's style guide unless you feed it in.
- **Trace data flow manually.** For any code touching authentication, authorization, or data persistence, trace the flow from entry to exit. Agents commonly miss edge cases in error handling, transaction boundaries, and cleanup paths.
- **Verify dependency choices.** When an agent adds an `import` or a new package, verify it against your [existing dependency policy](https://snyk.io/advisor/) and lockfile. The agent may suggest a package you have already excluded for security or licensing reasons.

## Security and Performance Considerations

Coding agents introduce a specific class of security risk: the developer-in-the-loop problem inverted. Traditionally, security vulnerabilities came from developers making mistakes. With agents, vulnerabilities come from developers *accepting* mistakes they did not make and therefore did not think through.

An agent generating a database query might not parameterize inputs correctly if the surrounding context does not make the ORM's query builder obvious. An agent setting up an authentication flow might store tokens in localStorage because that is the most common pattern in training data—even though your security requirements mandate httpOnly cookies. An agent adding an API endpoint might not implement rate limiting, input validation, or proper CORS headers unless explicitly instructed.

The performance dimension follows the same pattern. An agent will produce functionally correct code that may be wildly inefficient for your data scale. It does not know that the table has 40 million rows, that the API is called 10,000 times per minute, or that the lambda has a 128MB memory limit. Performance-aware engineering requires context that agents simply do not have unless you provide it—and providing it requires knowing it matters.

The security posture of AI-assisted codebases is not worse by necessity. It is worse when the humans in the loop lack the proficiency to catch what the agent misses. Experienced developers bring [threat modeling intuition](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html) that no amount of training data replicates.

## Limitations and Future Work

This argument has boundaries. Agent capabilities are improving rapidly—context windows are growing, retrieval mechanisms are getting better at surfacing relevant project context, and some agents can now read entire codebases before suggesting changes. The gap between "what the agent knows" and "what the developer knows" will narrow.

But the gap will not close to zero for several structural reasons. First, engineering decisions are often implicit. They live in commit messages, Slack threads, incident postmortems, and the developer's memory of why a particular approach was chosen. No amount of code context captures the full decision history. Second, correctness in software is domain-specific. An agent cannot know that your financial system must never round intermediate calculations, or that your healthcare application must log every data access for compliance, unless those constraints are explicitly encoded somewhere the agent reads.

Future work in agent tooling will likely address some of these gaps through better project-level memory (persistent context across sessions), intent-aware code generation (understanding *why* a pattern exists, not just *what* it is), and tighter feedback loops between validation tools and the generation process. But each of these advances makes the experienced developer more productive—it does not make the inexperienced developer equivalent. The ceiling rises with the floor.

The tools will keep getting better. The need to understand what you are building will not go away.

## FAQ

**Does this mean junior developers cannot benefit from coding agents?** Not at all. Junior developers benefit enormously—agents accelerate learning by showing how things can be done. But the learning still needs to happen. Using an agent as a crutch without understanding the output is the equivalent of copy-pasting from Stack Overflow without reading the explanation. It works until it does not, and when it breaks, you cannot debug what you do not understand.

**If I review every agent-generated diff, am I actually saving time?** Yes, because the review is faster than the generation. Writing fifty lines of boilerplate takes twenty minutes. Reviewing fifty lines of boilerplate to confirm it matches your patterns takes three minutes. The savings are real, especially for repetitive structural work like migrations, test scaffolding, and API endpoint plumbing.

**How do I build the technical proficiency this post argues for?** The same way it was always built: by writing systems, debugging production incidents, reading other people's code, contributing to open source, and working across different layers of the stack. Agents can accelerate this process (ask them to explain unfamiliar code, generate exercises, propose alternatives you had not considered), but the experience itself must be lived.

**Will future agents make this argument obsolete?** Potentially, but not in the near term. The structural limitations (implicit project knowledge, domain-specific correctness criteria, evolving team conventions) are not problems that scale with model size. They require architectural changes in how agents integrate with development workflows—persistent memory, intent modeling, and real-time convention enforcement. Those are active research areas, not shipped products.

**What is the difference between context-stuffing and genuine steering?** Context-stuffing is providing the agent with documents and hoping it figures out the relevance. Steering is knowing which constraint matters for this specific change and encoding it as a directive: "use the repository pattern, not direct DB queries" or "this module avoids framework X for latency reasons." The former is passive. The latter is active engineering judgment applied through a new interface.

The tools are extraordinary. Use them. But use them as someone who knows what they are building—not as someone hoping the machine knows for you.
